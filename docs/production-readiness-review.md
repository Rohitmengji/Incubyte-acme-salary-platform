# Production-readiness review (2026-11-19)

An independent pass over the whole application after the frontend phase. It looked for functional bugs, security issues, wrong financial calculations, authorisation gaps, slow queries, accessibility problems and missing tests.

**Ground rule: nothing is listed as fixed unless it was reproduced first, then checked again after the change.** Each fixed item names the test that fails on the old code and passes on the new code. Where a fix is in place but has no automated test, the table says so.

## How it was reviewed

- **Source review.** Three independent reviewers: security, backend correctness, and frontend behaviour and accessibility. Every claim was checked against the source before it was accepted. Some were rejected (see below).
- **A fresh 10,000-employee database** (`acme_review`), seeded with the deterministic seed. It has exactly 10,000 employees, and its dataset checksum matches the one in [performance.md](./performance.md).
- **Production builds** of the API (`dist/server.js`, `NODE_ENV=production`) and the web app (`next build`, `next start`) running against that database. Every security scenario was re-run against these builds after the fixes.
- **All test layers:**
  - **Unit and integration:** shared 24, API 153 (against real PostgreSQL), web 55 (React Testing Library).
  - **Playwright end to end:** 19 tests on a separate seeded 10k database, including axe scans and a phone viewport.
  - **Static checks:** lint, typecheck and format check all pass.
- **Dependencies:** `npm audit` reports 0 known vulnerabilities.

## Findings that were confirmed and fixed

Severity reflects the demonstrated effect in this app, not a generic rating.

## Checked and rejected

- **"Editing an inactive employee drops their status because the select is disabled."** React Hook Form still submits the value from form state. Two tests were added to keep it that way (`employee-dialogs.test.tsx`).
- **SQL injection and authorisation.** Every raw query is a Prisma tagged template with bound parameters, and every route has a role check with integration tests for allow and deny. Exports are manager-only: a viewer gets 403, which the benchmark itself ran into.

## Not fixed: known limits and trade-offs

- **The account lockout can be abused.** An attacker who knows an email can block that account's sign-in for 15 minutes with 30 wrong passwords. That's the usual trade-off of a per-account limit. MFA or SSO with adaptive throttling is the production answer.
- **Rate limits live in memory**, so they're per process. A multi-instance or serverless deployment needs a shared store (architecture §12).
- **`TRUST_FORWARDED_FOR=1` must only be set** when the web app sits behind an edge proxy that overwrites `X-Forwarded-For` itself.
- **Dashboard and analytics JS is about 377 KB compressed**, mostly the charting library. It's acceptable for an internal tool. Loading the charts lazily is the next step if it matters.
- **No automated tests** for the stale-version reload (B11), the salary-change dialog's fresh defaults (B10), or the histogram snapshot under concurrency (F3).

## Performance at 10,000 employees

The full method and numbers are in [performance.md](./performance.md#production-readiness-re-measurement). In short, on production builds:

- **Employee list:** p95 4.4 ms, deepest page 11 ms.
- **Dashboard queries:** each 31 ms or less.
- **24-month trend:** 248 ms.
- **Full CSV export:** 229 ms p95.
- **Under load:** with 50 concurrent clients, the list stays at p95 65 ms (about 880 requests per second).
